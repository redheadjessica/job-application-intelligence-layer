# Job Vetting System Instructions

This system is for job triage only: score and rank which jobs are worth applying to.

## Goal
Help the candidate decide which jobs are worth applying to before moving anything into the tailoring step. Scoring uses two files, both generated by the `/intake` skill:
- `PRIVATE__YOUR_FILES_GITIGNORED/03-VETTING__YOUR_PRIVATE_INFO/01-scoring-card.md` — the rubric (4 weighted dimensions + the candidate's custom factors)
- `PRIVATE__YOUR_FILES_GITIGNORED/03-VETTING__YOUR_PRIVATE_INFO/02-candidate-profile.md` — who the candidate is, their priority lanes, and practical constraints

## Standing Rules
- Prefer CSV output for spreadsheet use; also write a readable Markdown summary
- Output files (rankings CSV/MD/XLSX) go into the batch's `1 - Rankings/` tier under `__READY_TO_REVIEW__PRIVATE_GITIGNORED/<batch>/` when an out-dir is provided; otherwise alongside the scored job files
- Prefer `.txt` over `.pdf` when both exist for the same role; if only `.pdf` exists, read it directly
- Do not create `.txt` copies unless explicitly asked
- Do not recommend resume bases or generate application materials here (that is the tailoring step)
- Do not over-index on title
- Weight mission/role/craft fit and likely market perception per the scoring card's weights
- Optimize for high-leverage applications, not maximum volume

## Prep handoff (read before ranking)
Ranking reads **only** usable job posts from `3 - Source Material/All Job Posts (full text)/`. Prep quarantines thin/questionable fetches into `3 - Source Material/Needs Review/` and failed fetches into `3 - Source Material/Failed/` (siblings, not under the usable folder), so they are **never ranked by default**.

After running prep, read `0 - Prep Report/prep-report.md` and tell the user in plain language: how many usable posts are ready, what was skipped (duplicates), what needs review (thin/failed), where the report is, and whether it's safe to rank now. The machine-readable `0 - Prep Report/prep-manifest.json` is a cross-check, not a ranking dependency. To recover thin/failed posts, re-run the same prep command (it skips already-usable URLs and retries the rest).

## Personalization
Everything candidate-specific — lanes, comp floor, location, dealbreakers, strengths/gaps — lives in `02-candidate-profile.md`, with the high/low scoring signals in `01-scoring-card.md`. Both are produced by `/intake`. Keep this file generic: do not hardcode any one person's preferences here.

Structured numeric preferences (comp target/floor, home metro + aliases, lanes) live in `jail.config.json` (also from `/intake`). The scorer inlines it as `<preferences>` to sharpen `practicality_score`.

**The rankings output is a fixed 28-column contract (2026-07-30; `ATS Last Updated Date` added 2026-07-31).** The order is authoritative and
defined ONCE, in `norm_contracts.CONTRACT_TEMPLATE` + `resolve_contract_headers()`; `vet-jobs.js`
writes it, `normalize_rankings_csv` MIGRATES any older CSV to it in place (rename → drop → insert →
reorder, joined by header NAME so no column's data can shift), and `make_rankings_xlsx.py` shares the
same helper so a migrated CSV needs no further repair and a hand-made one still regenerates correctly.
`Location Fit` was **removed** as redundant with `Working Location`: the canonical grammar already
encodes remote/metro/cadence, both cells carried the same four hexes, and a second derived label was
one more thing to keep in sync. Two rules worth stating plainly. **`ATS First Posted Date`** and **`ATS Last Updated Date`** share
ONE convention: each holds the ATS's own date when the board publishes it, and otherwise the literal
`Unknown` — **neither is ever blank**. (An earlier revision had the update column use blank instead;
that was superseded on 2026-07-31 because two adjacent date columns with two different empty
conventions is a trap — a reader cannot tell "nothing to look up" from "we failed to look", and a
blank cell reads as unfinished work.) Neither date is ever substituted with JAIL's fetch date, a
file date, a deadline, a syndicated-listing date, or anything inferred from the posting's wording;
the update value comes only from ATS metadata already stored in the capture; and **neither feeds
scoring, ranking, or prioritization**, and **only** columns marked `[You Fill In]` /
`[You Change]` / `[You Add]` are human-managed — a bare `?` in a header does not imply it
(`Tailored? (Base Resume)` and `Cover Letter Drafted?` are written by the pipeline via
`update_rankings_row.py`, which accepts both header generations on read). A column a user added
themselves is never dropped by the migration.

**Captures arrive in the JOB SNAPSHOT format, with ORIGINAL vs LATEST capture details.** Prep writes a
human-readable preamble — `JOB SNAPSHOT` (incl. `Job Posted At:` / `Job Updated At:`, always present,
`Unknown` when the source exposed none) / `WORK DETAILS` (incl. an optional `Location Preference:` when
the employer states one) / `COMPENSATION` / `APPLICATION QUESTIONS WORTH PREPARING` — then the job text
between the unchanged `--- JOB TEXT START/END ---` markers, then `ORIGINAL CAPTURE DETAILS` and (only on
a re-fetch) `LATEST CAPTURE DETAILS` BELOW the end marker. Read the WORK DETAILS / COMPENSATION sections
as ground truth rather than re-deriving from body prose; their honest sentence-case phrases mean exactly
what they say (`Employer did not mention <X>.` = published nothing; `Could not verify.` = the capture
failed; `Conflicting employer information: …` = two sources disagree; `Not Specified` = no cadence
stated, never invent one). The machine record stays the manifest's `field_status`. A posting's capture
history lives in a durable gitignored registry (batch manifests mirror it), where the ORIGINAL capture
is immutable and means *the earliest capture JAIL can establish from its durable records* —
`Job Posted At:` is the EMPLOYER's date and is never conflated with either capture timestamp.

**Two different coloring regimes — don't merge them:**
- **Comp Fit and Lane Fit are candidate-relative from the config** (comp vs floor/target via the midpoint rule; Lane Fit vs the matched lane's priority). Missing or partial config → those colors fall back to **neutral** and the report says so. Don't hardcode a salary tier here; it belongs in the user's config.
- **Working Location is a fixed contract, by design** (authoritative output-contract spec, 2026-07-29). It is colored deterministically from the *normalized* location text with exactly four hexes — green `42FF35` genuinely-available remote, yellow `FDFF43` acceptable home-metro office at exactly 1–3 days, orange `FA9C31` unknown / known-city-unknown-cadence / >3 days / open-ended minimums (`3+`, "at least 3"), red `F82C1F` required in-person outside the acceptable geography. **No grey, ever.** `location.arrangements` does NOT drive this color (it is a scoring signal only); which cities count as home metro comes from `home_metro` + `home_metro_aliases`, never from `city_priority`. Yes, this deliberately hardcodes "genuinely-available remote is green" for this column — that was the explicit instruction, and it is enforced in ONE place: `norm_contracts.working_location_color()`.

**`Status` is a fixed vocabulary, repaired not trusted.** The 12 lifecycle values are defined once, in `norm_contracts.STATUS_VALUES` (`make_rankings_xlsx` imports them for the dropdown and the color maps — never add a second copy). `normalize_status()` repairs case/spacing/punctuation drift to the exact canonical spelling, because a near-miss like `Apply if Time` silently costs the cell its dropdown match, its lifecycle fill, and its filter grouping, and `run-batch.js` compares the skip-band status by string equality. A value matching nothing is left **exactly as written** and warned about — the column is the candidate's, so flagging beats mangling. Repair touches spelling only; it never reassigns a status.

**Output contracts are enforced mechanically, not by prompt.** `ENGINE__PUBLIC_GIT_TRACKED/03-VETTING/norm_contracts.py` is the single home for the Working Location grammar, Comp Range format, Comp Fit label, Lane taxonomy, and canonical tailored-application names. It runs as a CLI pass over the rankings CSV right after scoring, and `make_rankings_xlsx.py` imports it and re-normalizes **on read**, so regenerating an old CSV repairs it too. Prompts may still describe the target shape, but never rely on the model to honor it.

**Every score gets a prose companion column — never write rationale into a contract-owned cell.** `Your Desire Score Notes`, `Profile Score Notes`, `Top Reasons Notes`, `Top Concerns Notes` and `Comp + Lifestyle Fit Notes` are where reasoning goes (the first two were `Mission Fit Notes` / `Scope Fit Notes` before the 2026-07-30 contract). `Comp + Lifestyle Fit Notes` is the rationale/audit trail for the `Comp + Lifestyle Fit Score` and carries that dimension's breakdown in a terse `cash | location | equity+bonus+benefits` shape. `Comp Range` (mechanical `N-N`) and `Comp Fit` (machine-derived by `norm_contracts.comp_fit_label()`) are NOT places for prose: the normalization pass re-derives them on every run, so anything narrative written there is silently destroyed. That is exactly what happened before this column existed. The notes header is a static string even though the score label is candidate-relabelable, because both Python passes locate the column by name; for an older CSV, `norm_contracts.practicality_notes_insert_at()` inserts it positionally (anchored on the score column, falling back to `Mission Fit Notes`) with an empty value — the same insert-plus-back-fill convention as `Job Posted Date` and `Data Completeness`, so no other column's data shifts.

**Lane vs Lane Fit (don't conflate):** **`Lane`** is the job's *actual* category in the job's own terms (what the role IS), independent of the candidate. Its format is a fixed taxonomy: `<Bucket> - <short descriptor>` with buckets **Health / Consumer / Work / Other** (e.g. `Work - Collaboration`, `Health - Mental Health`, `Consumer - Marketplace`) — enforced by `norm_contracts.normalize_lane()`. Slash-only forms like `"Product Strategy / AI Research"` are NOT valid Lane values. **`Lane Fit`** is the candidate-relative judgment — which of the candidate's priority lanes it maps to, or "Outside lanes", with a confidence. A role can have `Lane = "Work - Collaboration"` *and* `Lane Fit = "Outside lanes (high)"`; that is correct, not a contradiction. It is the **Lane Fit** cell that is stoplight-colored by the matched lane's priority (p1 green / p2+ amber / Outside red); the `Lane` cell itself only distinguishes the Health bucket.

**Tracker output:** the rankings CSV + XLSX are a job-search tracker — human-editable columns (headers ending `? [You …]`) first, AI scoring/detail to the right. The XLSX adds: the header frozen + every cell wrapped/centered/top; an inline Status dropdown (the 12 lifecycle values) + auto-filter on the job rows (which have **no merged cells, so they sort cleanly**); lifecycle Status colors + Lane Fit / Comp Fit / Working Location / Data Completeness fills; an Instructions tab; and a **separate section-color legend block** (merged A:J bars) below the jobs to copy from when grouping. The data ships ungrouped in score order — users sort/group themselves. Generated `Status` values are always one of the dropdown values (lowest band is `Apply Eventually: Or Skip It`, score < 60). The canonical fit math and every output contract live in `norm_contracts.py` (single source); `vet-jobs.js` shells out to it after scoring and `make_rankings_xlsx.py` imports it, re-normalizing text and re-deriving Comp Fit + location colors on read — so it does more than map labels to colors.
